## What is a state and how do you create one?

To create a state, add the `@State` annotation to a *suspend* function:

```kotlin
@State
suspend fun main() {

}
```

You can also specify its name in the `@State` annotation parameters. This is optional; if omitted, the function name is used.
If you ever decide to rename the function, use a stable name inside `@State` so existing saves are not broken.

The idea is that you can use timers and waiting operations inside these functions.
For example, you can write a dialogue with pauses:

```kotlin
@State
suspend fun main() {
    println("Greetings, traveler")
    wait(2.sec)
    println("How are you doing?")
    wait(2.sec)
    println("Could you help me with one request?")
}
```

You can do the same through `onUpdate`, but the result is much more verbose:

```kotlin
var ticker = 0
var phrase = 0

onUpdate {
    // If the dialogue is over, the counter no longer updates
    if (phrase > 2) return@onUpdate

    // If the tick count is greater than 40 (equivalent to 2 seconds)
    if (ticker > 40) {
        ticker = 0 // Reset the counter so the next phrase appears after 2 seconds
        when (phrase) { // Write the current phrase
            0 -> println("Greetings, traveler")
            1 -> println("How are you doing?")
            2 -> println("Could you help me with one request?")
        }
        phrase++ // Switch to the next phrase
    }
    ticker++ // Update the counter every tick
}
```

Coroutines make this much simpler and more compact.
<br/>
The remaining question is how to save the state when it has not finished before the player leaves, so they do not have to reread a 40-minute dialogue from the beginning. That is what the next sections cover.

## Saving state data

In the current architecture, the engine does not automatically save the full script execution state. Instead, it saves:

- the name of the current state;
- the current state's `stateTag`;
- child states started through `async`;
- separate script data from `onSave` / `onLoad`.

This means that after the world is reloaded, the last running state starts again with the same `stateTag`; it does not resume from the exact same bytecode line. Therefore, every important step that must not be repeated should be marked through `stateTag`, `runOnce`, or `remember`.

### `stateTag()`

`stateTag()` is a function that returns a `CompoundTag`: a data container bound to the current state. It is saved together with the script and restored on the next world load.

A minimal example:

```kotlin
@State
suspend fun main() {
    val tag = stateTag()
    if (!tag.getBoolean("greeting_shown")) {
        println("Greetings, traveler")
        tag.putBoolean("greeting_shown", true)
    }

    wait(2.sec)

    if (!tag.getBoolean("question_shown")) {
        println("Could you help me with one request?")
        tag.putBoolean("question_shown", true)
    }
}
```

If the server saves and shuts down between the two phrases, the `main` state will start from the beginning on the next launch, but the first phrase will not repeat because the `greeting_shown` flag is stored in `stateTag`.

Usually, `stateTag()` should contain only compact and stable data:

- flags for actions that have already completed;
- step numbers;
- UUIDs of entities or players;
- selected dialogue options, if they are not used by other states;
- simple values that can be written to NBT.

Do not keep `Entity`, `Player`, or other live objects in local variables if they still need to be valid after `wait`, `delay`, `await`, or a world reload. For entities and players, store UUIDs or use `Ref`, described below.

### How is `stateTag()` different from `onSave()` / `onLoad()`?

A `*.node.kts` script has two save levels.

The first level is user-defined node data, saved through the `onSave` / `onLoad` handlers described in [Introduction to Node Scripts](/docs/hollowengine/scripting/node):

```kotlin
onSave { context ->
    context.tag.putInt("reputation", reputation)
}

onLoad { context ->
    reputation = context.tag.getInt("reputation")
}
```

This data is saved separately from states. It is convenient for global node state: reputation, quest progress, user settings, caches, and other data that does not belong to a specific state.

The second level is active state data. It is stored in `stateTag()` and is needed specifically to restore a scenario: which step has already been completed, which NPC was created, or which dialogue branch the player chose.

Simplified, it looks like this:

```text
node.nbt
├─ extras  -> data from onSave / onLoad
└─ states  -> active StateContext
   ├─ next_state
   ├─ self     -> stateTag
   └─ children -> child async states
```

The rule is simple:

- save **node data** through `onSave` / `onLoad`;
- save **data for a specific state execution** through `stateTag`, `runOnce`, `remember`, and `forget`.

## Switching between multiple states

States can be split into small functions and switched between them.

```kotlin
@State
suspend fun main() {
    println("Need to talk to the blacksmith")
    wait(1.sec)

    blacksmithDialog()
}

@State(name = "blacksmith")
suspend fun blacksmithDialog() {
    println("Blacksmith: I need ore from the old mine")
    wait(2.sec)

    mineQuest()
}

@State(name = "mine_quest")
suspend fun mineQuest() {
    println("Quest updated: find the old mine")
}
```

Important: calling one `@State suspend` function from another `@State suspend` function is **not a normal nested function call**.
The HollowEngine compiler plugin replaces such a call at the IR stage with a transition to another state.
**That means there is no return to the previous function after the `@State` function finishes.**

This approach makes transitions explicit for the runtime: the engine changes `nextState`, finishes the current state, and then starts the next one.

## Helper functions

### `runOnce`

`runOnce` is used for actions that must not repeat after a state restart.

```kotlin
@State
suspend fun main() {
    runOnce("give_map") {
        println("The player received a map")
        // player.update { inventory.add(ItemStack(...)) }
    }

    wait(10.sec)
    println("This text may run after restoration")
}
```

Under the hood, this uses the same idea as a manual flag in `stateTag()`: if the key is already marked as completed, the block will not run again.

Use `runOnce` for irreversible actions:

- giving an item;
- spawning an NPC;
- changing blocks in the world;
- sending a one-time message;
- granting a reward;
- playing a long dialogue.

### `remember`

`remember` is useful when you need to calculate a value once and reuse it when the state starts again.

For example, if a state creates an NPC, do not create it again after every world load. Remember its UUID and then work with it through `entityRef`:

```kotlin
@State
suspend fun main() {
    val traderId = remember("trader_uuid") {
        spawnTrader().uuid
    }

    val trader = entityRef<LivingEntity>(traderId)

    trader.update {
        customName = "Mysterious Trader".literal
    }
}
```

### `forget`

`forget` removes a saved value if the scenario needs to be played again.

```kotlin
@State
suspend fun resetQuest() {
    forget("trader_uuid")
    forget("give_map")

    main() // Note: this means a normal suspend function, not a State. When switching to another State, it has a different stateTag().
}
```

This is useful for repeatable scenes, testing, rolling back a dialogue branch, or restarting a quest.

## Waiting that survives a restart

Plain `wait(ticks)` (see [Utility Methods](/docs/hollowengine/scripting/npc/methods)) is just a timer, if the state restarts while it is still counting down, per the rules at the top of this page, the state begins again from the top and the countdown starts over from scratch. That is fine for short pauses inside a dialogue, but not for something like "wait 5 minutes" or "once a day" that needs to keep counting even across a server restart.

For that, give the wait a stable `name`, the same way `runOnce` and `remember` use one, and it will remember where it left off:

```kotlin
@State
suspend fun main() {
    wait(20 * 60 * 5, "patrol_pause") // 5 in-game minutes, counted only while the server is running
}
```

There are two more variants for real-world time, including time the server was completely shut down:

```kotlin
@State
suspend fun main() {
    npc.say("Come back tomorrow for a reward!")
    wait(1.days, "daily_reward_cooldown") // counts real time, even while the server is offline
    npc.say("Your reward is ready!")
}
```

```kotlin
@State
suspend fun main() {
    wait(Instant.parse("2026-12-25T00:00:00Z"), "christmas_event") // waits until an absolute date
    npc.say("Happy holidays!")
}
```

| Function | Counts | Keeps counting while the server is offline? |
|----------|--------|-----------------------------------------------|
| `wait(ticks)` | in-game ticks | No, the countdown restarts from scratch if the state restarts. |
| `wait(ticks, name)` | in-game ticks | No, but it resumes the same countdown from where it left off, instead of starting over. |
| `wait(duration, name)` | real wall-clock time | Yes. |
| `wait(instant, name)` | real wall-clock time, until a fixed date | Yes. |

Just like `runOnce` and `remember`, the deadline is stored in the current state's `stateTag()`, so it follows the same save/restore and naming rules described earlier on this page. Use a different `name` for every persistent wait in your script so they don't overwrite each other.

## Launching

Launching is also done with a command. The only difference is that you explicitly provide the state / function name:

```mcfunction
/hollowengine scripting run scripts/your_script.node.kts startQuest
```

And to stop it:

```mcfunction
/hollowengine scripting stop scripts/your_script.node.kts
```

## Story logic

During scenarios, it is often tempting to store an NPC or player in a variable and keep working with it after `wait`:

```kotlin
@State
suspend fun main() {
    val npc = spawnTrader()
    wait(60.sec)
    npc.remove(RemovalReason.DISCARDED)
}
```

This code looks convenient, but it has a problem: during the wait, the entity may unload, die, change level, or become invalid. For long scenarios, it is better to store not the object itself, but a `Ref<T>` reference.

`Ref<T>` can:

- check whether the reference is alive through `isLinkAlive`;
- wait for the object through `resolve()`;
- safely read data through `read { ... }`;
- safely update the object through `update { ... }`.

Example with an NPC:

```kotlin
@State
suspend fun main() {
    val npcId = remember("trader_uuid") {
        npc(pos(x, y, z), name="Trader").uuid
    }

    val trader = entityRef<LivingEntity>(npcId)

    wait(60.sec)

    // If the NPC has unloaded from the chunk, the script will wait until the chunks are loaded again
    trader.update {
        remove(Entity.RemovalReason.DISCARDED)
    }
}
```

Example with a player:

```kotlin
@State
suspend fun main() {
    val player = playerRef("Steve") // You can get a reference by nickname or UUID: `playerRef(uuid("12346-..."))`

    player.update {
        send("Are you ready?")
    }
}
```

If you need to resolve several references at once and make sure they are still valid, use `borrow`:

```kotlin
@State
suspend fun attackTarget() {
    val attacker = entityRef<LivingEntity>(stateTag.getUUID("attacker"))
    val target = entityRef<LivingEntity>(stateTag.getUUID("target"))

    borrow(attacker, target) { me, them ->
        me.doHurtTarget(them)
    }
}
```

`borrow` is needed for situations where one entity could unload while the first and second references are being resolved. It repeats the resolution until all references are alive at the same time.

The main rule for story scenarios:

```text
short action right now or near the player -> you can work with Entity / Player
long scenario with wait/await/requestItems -> store UUIDs and use Ref<T>
```

This keeps states resilient to chunk unloading, player logout, and world saves.
