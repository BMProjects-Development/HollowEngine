<center><h1>Script Imports</h1></center>

Move shared functions into a separate file and import them into other scripts. You can then update the function in one place for all its callers.

![Script import navigation in the IDE](/hollowengine/pictures/ide/code-navigation.webp)

Add `@file:Import(...)` at the start of the file. The fragment below shows the syntax: `example.kts` must exist and declare `functionFromExample()`.

```kotlin
@file:Import("example.kts")

functionFromExample()
```

The path is resolved relative to the current script. For this structure:

```text
hollowengine/
└─ scripts/
   ├─ quest/intro.node.kts
   └─ common/dialogue.kts
```

the `quest/intro.node.kts` script imports `common/dialogue.kts` like this:

```kotlin
@file:Import("../common/dialogue.kts")

runSomeDialogue()
```

That means two dots move one folder up relative to the current file. If the scripts are in the same folder, you can simply specify the file name.

Several scripts go into one annotation rather than several in a row (`@file:Import` is one per script):

```kotlin
@file:Import("../common/dialogue.kts", "../common/rewards.kts")
```

:::warning
`@file:Import(...)` must appear before classic declaration imports such as `import net.minecraft.world.entity.player.Player`.
:::

## What gets imported?

An imported script also runs its top-level code. If it creates an object or prints a message outside a function, importing it performs that action. Its variables, functions, and classes then become available to the importing script.

Create the two files below. `sayLine` receives a player parameter, while the calling node waits for the player `Steve` to join. Replace the name with yours and run the `main` state.

```kotlin
// common/dialogue.kts
import net.minecraft.network.chat.Component
import net.minecraft.world.entity.player.Player

val narratorName = "Guide"

fun sayLine(player: Player, text: String) {
    player.sendSystemMessage(Component.literal("$narratorName: $text"))
}
```

```kotlin
// quest/intro.node.kts
@file:Import("../common/dialogue.kts")

@State
suspend fun main() {
    playerRef("Steve").update {
        sayLine(this, "The bridge is closed.")
    }
}
```

## Equal names

The declarations of all imported scripts end up in one space. When two scripts declare something with the same name, the declarations themselves are fine, but a reference to that name does not compile (`Overload resolution ambiguity`): the compiler cannot tell which of the two you mean.

```kotlin
// common/dialogue.kts
val title = "Dialogue"
```

```kotlin
// common/rewards.kts
val title = "Rewards"
```

```kotlin
@file:Import("../common/dialogue.kts", "../common/rewards.kts")

println(title) // Error: which of the two `title`s?
```

The simplest fix is to give the declarations different names. When that is inconvenient, give each script a package of its own with a `package` line, as in a regular Kotlin file:

```kotlin
// common/dialogue.kts
package mypack.dialogue

val title = "Dialogue"
```

```kotlin
// common/rewards.kts
package mypack.rewards

val title = "Rewards"
```

After that the script's declarations are reached by their full name or through a regular `import`, including one under another name:

```kotlin
@file:Import("../common/dialogue.kts", "../common/rewards.kts")

import mypack.dialogue.title as dialogueTitle
import mypack.rewards.*

println(dialogueTitle) // Dialogue
println(title) // Rewards, brought in by `import mypack.rewards.*`
```

:::warning
The top of a file goes in this order: `@file:...` annotations first, then `package`, then the regular `import`s.
:::

A script's package is only a name for Kotlin. It changes neither the path in `@file:Import` nor the namespace of the items and blocks a startup script registers.

## Sharing scripts

By default, an imported script runs separately from the script into which it is imported. In other words, if you create a variable and modify it in one script, by default it will not change in the other script. You can change this by adding `@file:SharedScript` if you want the script to be shared when imported into any other scripts:

```kotlin
// common/dialogue.kts
@file:SharedScript

val dialogueHistory = mutableListOf<String>()

fun sayLine(text: String) {
    dialogueHistory += text
}
```

In that case, all scripts that import `common/dialogue.kts` will access the same instance and the shared `dialogueHistory`. This is useful for services that share state during gameplay. For example, a dialogue system that is read from `.reload.kts` or `.mixin.kts` and modified within `.node.kts`.

`SharedScript` is imported by default, meaning a separate `import ...` statement is not required for it. The annotation must be placed at the beginning of the file, before the regular imports.

[Startup scripts](/docs/hollowengine/scripting/startup#using-it-from-other-scripts) are always shared, even without the annotation: an import hands over the instance that ran while the game started, and it is not reset when you leave a world.

A shared script compiles into its own cache artifact and uses one instance across importing scripts. Closing the world’s server clears that instance. Startup scripts keep their instance until the game exits.

:::warning
Changing a shared script during play can leave running scripts with old classes while reloaded scripts receive new ones.

Check persistence carefully: `/reload` removes old handlers but does not repeat the server-start event. If shared state is loaded and saved by those events, new handlers may receive empty data and overwrite the previous state later.

Save the world before editing a shared script. After the edit, restart the world or game and check that data is restored.
:::
