<center><h1>Custom Data</h1></center>

*Give an NPC, a player, or any entity its own typed, saved data, without touching raw NBT tags.*

## `.data`: data that belongs to the entity itself

Every entity has `.data`, a small typed storage that is saved and restored automatically together with its owner, forever, regardless of which script, state, or handler is currently running. This works on `npc`, on a `player`, and on any other `Entity`. This is the right place for things like reputation, a shop's stock, or "has this NPC met the player before".

First declare a key, once, at the top of your script (or in a separate script you import from several places):

```kotlin
val REPUTATION = dataKey<Int>("reputation") { 0 } // 0 is the default value if never set
```

Then use it anywhere you have the entity:

```kotlin
val current = npc.data[REPUTATION]               // Int? - null only if there's no default and it was never set
val current2 = npc.data.getOrPut(REPUTATION)      // Int - falls back to the default and stores it
npc.data[REPUTATION] = current2 + 1
npc.data.update(REPUTATION) { it + 1 }            // read-modify-write in one call
REPUTATION in npc.data                            // Boolean
npc.data.remove(REPUTATION)                       // Boolean, true if it existed
```

`dataKey<T>(name)` works for `Int`, `String`, `Boolean`, and other simple types out of the box.

The same calls work on a player:

```kotlin
val VISITS = dataKey<Int>("visits") { 0 }

player.data.update(VISITS) { it + 1 }
```

:::advice
Because `.data` lives on the entity itself, it works from anywhere: a `@State` scene, an `onInteract`/`onHurt` handler on a [node script attached to the entity](/docs/hollowengine/scripting/node), or a plain `.reload.kts` event handler. It does not need a running story or an active `@State`.
:::

## Syncing to the client

By default `.data` lives on the server only. When the client needs a value - a UI, an animator, a hint under the crosshair - declare the key with a sync policy:

```kotlin
val QUEST_GIVER = dataKey<Boolean>("quest_giver", sync = Sync.TRACKING) { false }
val STAMINA = dataKey<Float>("stamina", sync = Sync.OWNER) { 1f }

npc.data[QUEST_GIVER] = true // the clients hear about it at the end of the same tick
```

| Policy | Who receives the value |
|--------|------------------------|
| `Sync.NEVER` (default) | Nobody, the value stays on the server. |
| `Sync.TRACKING` | Every client that can see the entity. For what is on show anyway: an NPC's role, its mood, whether the shop is open. |
| `Sync.OWNER` | The player itself and nobody else. For a player's own state - quest progress, stamina - that everyone standing nearby has no business receiving. On a non-player entity this is the same as `Sync.NEVER`. |

There is no separate "send": writing a synced key marks the entity by itself, and one packet carrying the difference goes out at the end of the server tick, together with that entity's components - so data never arrives before the model it belongs to. A client that has just started seeing the entity gets a full snapshot.

The client reads it through the same `.data`, and in a UI it reads reactively: the screen recomposes itself when the server sends a new value.

```kotlin
// .ui.kts
import net.minecraft.client.Minecraft
val QUEST_GIVER = dataKey<Boolean>("quest_giver", sync = Sync.TRACKING) { false }

overlay("mypack:interact_hint") {
    anchor = "crosshair"
    autoShow = true
    rebuildEveryFrame = true // the crosshair target changes every frame, not per packet
    content {
        val target = Minecraft.getInstance().crosshairPickEntity ?: return@content
        if (target.data[QUEST_GIVER] == true) Text("Press F to talk")
    }
}
```

The value has one owner, the server. A synced key written on the client survives only until the next packet, and the engine says so in the log. A plain (`Sync.NEVER`) key written on the client, on the other hand, goes nowhere and is never overwritten - that is the right place for purely client-side scratch such as the current hover target.

### In animator conditions

The numeric values of synced keys are visible to [expressions](/docs/hollowengine/scripting/animator-editor) under the `d.` prefix, addressed by their path inside the NBT. That is how a server script turns an animation layer on without sending anything by hand:

```kotlin
@Serializable data class Emotion(val happy: Float = 0f, val angry: Float = 0f)
val EMOTION = dataKey<Emotion>("emotion", sync = Sync.TRACKING) { Emotion() }

npc.data[EMOTION] = Emotion(happy = 1f)
```

```text
d.emotion.happy > 0.5
```

A path that is not set, or that holds text rather than a number, reads as `0`, like any other unknown variable.

## Persistence and lifetime

`.data` is saved with the rest of the entity's state, so it follows its owner the same way the engine's other per-entity state does:

- For a regular entity (an NPC, a mob, anything), it is written to disk with the entity and reloaded when the chunk loads back.
- It survives a dimension change, including a trip through a portal or the End.
- For a player, it also survives death: the data set before `PlayerEvent.Clone` is still there on the respawned player object, no manual copying required.

An entity that never touches its own `.data` keeps no backing storage and adds nothing to its saved NBT, so most mobs in a world that never read or write it pay no extra cost.

## The state-scoped equivalent: `stateGet` / `stateSet`

[States and Coroutines](/docs/hollowengine/scripting/node/states) already introduced `stateTag()`, a raw NBT container tied to the *currently running state*. The same `DataKey` idea works there too, as a typed shortcut instead of calling `tag.putInt(...)` / `tag.getInt(...)` by hand:

```kotlin
val VISITS = dataKey<Int>("visits") { 0 }

@State
suspend fun main() {
    val visits = stateGetOrPut(VISITS)
    stateSet(VISITS, visits + 1)

    if (visits == 0) {
        npc.say("We haven't met before!")
    }
}
```

`stateGet`, `stateGetOrPut`, `stateSet`, `stateUpdate`, `stateContains`, and `stateRemove` all mirror the `.data` functions above one for one, they just read and write `stateTag()` instead of the entity's own storage. They must be called from a `suspend` function running inside a `@State`, exactly like `stateTag()` itself.

## Where should I store what?

| Storage | Lifetime | Needs an active `@State`? |
|---------|----------|----------------------------|
| `.data` (`npc.data`, `player.data`, ...) | Lives with the entity forever, including across death (players) and dimension changes. | No, works anywhere. |
| `stateGet` / `stateSet` / `stateTag()` | Lives with the current state, and is cleared or replaced the way [States and Coroutines](/docs/hollowengine/scripting/node/states#saving-state-data) describes. | Yes. |
| `onSave` / `onLoad` or `persisted(...)` on a [node script](/docs/hollowengine/scripting/node) | Lives with that specific node script's own attachment. | No, it's a separate lifecycle entirely. |

As a rule of thumb: if the data describes the entity itself (reputation, known players, unlocked dialogue), use `.data`. If it describes progress through a specific scene or quest step, use `stateTag()` / `stateGet` / `stateSet`.
