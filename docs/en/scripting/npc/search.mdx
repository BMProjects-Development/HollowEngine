<center><h1>Finding Entities and Items</h1></center>

*Ask an NPC what is around it: players, other NPCs, any entity, or dropped items.*

The examples below are fragments of a server `.node.kts` script. `npc` is a character returned by `npc(...)` or `this@NpcEntity` in an [attached node](/docs/hollowengine/scripting/node). `player` represents the server player from an interaction handler. Put calls that wait for completion inside `onStart`, `onInteract`, or an `@State suspend fun`.

## Quick helpers

For the common cases, you don't need to build anything, just call one of these:

```kotlin
val nearbyPlayers = npc.findPlayers(radius = 10.0)
val nearbyNpcs = npc.findNpcs(radius = 10.0) { other -> other.uuid != npc.uuid }
val nearestBread = npc.findNearestItem(itemFilter(item("minecraft:bread")), radius = 8.0)
```

| Function | Returns |
|----------|---------|
| `findPlayers(radius, filter)` | Players around the NPC, nearest first. |
| `findNpcs(radius, filter)` | Other NPCs around the NPC, nearest first. |
| `findItems(filter, radius, limit)` | Dropped items matching an [`ItemFilter`](/docs/hollowengine/scripting/npc/inventory), nearest first. |
| `findNearestItem(filter, radius)` | Just the single nearest matching dropped item, or `null` if there is none. |

Every result is a `Ref<T>`, the same reference type used for [remembering entities across a story](/docs/hollowengine/scripting/node/states#story-logic), not the raw entity. That is on purpose: by the time you actually use the result, the entity might have moved to another chunk, or even unloaded, and a `Ref` knows how to wait for it and re-find it safely.

```kotlin
val playerRef = npc.findPlayers(radius = 10.0).firstOrNull() ?: return
val player = playerRef.resolve() // safely get the live entity
```

## Building a custom search

For anything more specific than "nearby players", use `entityQuery<T> { ... }` to describe exactly what you're looking for, then pass it to `findEntities(...)` or `findNearestEntity(...)`:

```kotlin
import net.minecraft.world.entity.monster.Zombie

val query = entityQuery<Zombie> {
    radius = 24.0
    aliveOnly = true
    visibleOnly = true       // only entities the NPC actually has line of sight to
    limit = 5
    sort = EntityQuerySort.NEAREST
    filter { zombie -> !zombie.isBaby }
}

val zombies: List<Ref<Zombie>> = npc.findEntities(query)
val closest: Ref<Zombie>? = npc.findNearestEntity(query)
```

| Setting | Default | Meaning |
|---------|---------|---------|
| `radius` | `16.0` | Search radius around the NPC. |
| `aliveOnly` | `true` | Skip dead/removed entities. |
| `visibleOnly` | `false` | Only include entities the NPC has a direct line of sight to. |
| `limit` | unlimited | Maximum number of results. |
| `sort` | `EntityQuerySort.NEAREST` | `NEAREST`, `FARTHEST`, or `NONE` (no particular order, fastest). |
| `filter { ... }` | none | Add as many extra conditions as you like; you can call `filter { ... }` more than once, and an entity must pass all of them. |

`findNearestEntity(query)` is just a shortcut that forces `limit = 1` and `sort = NEAREST` for you, so you get a single `Ref<T>?` instead of a list.

## A note on `Ref<T>` and types

Specify the expected entity type in `findEntities<T>` and `entityRef<T>(uuid)`. For example, `<Zombie>` means “find a zombie,” so editor hints show its properties. If the UUID belongs to a different entity type, `resolve()` fails.

A `Ref` helps find the entity again after a wait or chunk load; it does not revive a removed character. Allow the scenario to be cancelled if its target can no longer appear.
