<center><h1>UI Script Files</h1></center>

UI declarations are Kotlin scripts with the `.ui.kts` suffix. Store them under `hollowengine/scripts`; nested folders are supported. The client compiles and executes them on resource reload. The Kotlin scripting compiler addon must be installed on the client.

The script has `UiScript` as its base class and imports the UI, widget, layout, style, `DataKey`, and HUD APIs automatically.

## Screens

`screen(id) { ... }` registers a screen. The id is a resource location used later by the server.

```kotlin
screen("mypack:settings") {
    title = "Settings"
    closeOnEscape = true
    pausesGame = false
    content {
        Column(modifier = Modifier.padding(12.px).gap(8.px)) {
            Text("Settings")
            Checkbox(checked = data[ShowHints], onCheckedChange = { checked ->
                send { putBoolean("showHints", checked) }
            })
        }
    }
}
```

`title` defaults to the id path, `closeOnEscape` defaults to `true`, and `pausesGame` defaults to `false`. Set `rebuildEveryFrame = true` only for content that reads live client state every frame.

## Replacing existing screens

`override(...)` makes a scripted screen stand in for a vanilla or modded one: whenever the game opens that screen, the player gets this one instead.

```kotlin
import net.minecraft.client.gui.screens.TitleScreen

screen("mypack:main_menu") {
    override(TitleScreen::class)
    content { MainMenu() }
}
```

The swap is client-side and needs no server, so it holds at the main menu, before any world is loaded. That also means an overriding screen has no session: `data` is empty and answers only with its keys' defaults, and `send { }` goes nowhere. Client state and `mc` are all it has.

`override(target, subclasses = true)` widens the match to anything extending `target`, for a screen a mod has subclassed. A screen that a script cannot import is named by class name instead:

```kotlin
override("com.example.mod.FancyScreen")
```

One declaration may override several screens. `LocalReplacedScreen` holds the screen that was replaced, which is how content tells its targets apart and hands work back to the original:

```kotlin
screen("mypack:menus") {
    override(TitleScreen::class)
    override(PauseScreen::class)
    content {
        when (LocalReplacedScreen.current) {
            is TitleScreen -> MainMenu()
            else -> PauseMenu()
        }
    }
}
```

| Rule | Meaning |
| --- | --- |
| Last script wins | Two scripts overriding the same class: the one loaded later takes it, and a warning is logged |
| Engine screens are never replaced | HollowUi's own Compose screens are skipped, so a broad override cannot swallow the engine's UI |
| Reload rebuilds the open override | The screen is rebuilt from the new script; if the override is gone the screen closes |

The replaced screen has already been detached by the time the swap happens, so container screens (an inventory and anything else backed by a menu) are not a supported target - their menu is closed with them.

## HUD overlays

`overlay(id) { ... }` registers a HUD layer. It may be server-driven or purely client-owned.

```kotlin
overlay("mypack:stamina") {
    anchor = "experience_bar"
    placement = HudPlacement.BEFORE
    autoShow = true
    content {
        val value = data[Stamina].coerceIn(0f, 1f)
        Box(modifier = Modifier.size((182f * value).px, 5.px).background(UiColor(0.3f, 0.8f, 1f)))
    }
}
```

| Option | Default | Meaning |
| --- | --- | --- |
| `anchor` | `hotbar` | Vanilla HUD layer to draw next to; bare names such as `crosshair` and `experience_bar` are accepted |
| `placement` | `HudPlacement.AFTER` | Draw before or after the anchor |
| `autoShow` | `false` | Show immediately after the script reloads; use for client-only HUD |
| `input` | `OverlayInput.NONE` | `NONE` for draw-only HUD, `INTERACTIVE` to receive input |
| `aboveScreens` | `false` | Also draw over an open screen |
| `rebuildEveryFrame` | `false` | Recompose each frame; enable only when necessary |

`interactive()` is shorthand for `input = OverlayInput.INTERACTIVE`. During gameplay, an interactive overlay uses the screen centre until it receives a pointer event.

## Adaptive surfaces

`surface(id)` is for UI that alternates between a HUD overlay and a full screen. For example, a dialogue can stay over gameplay until an answer requires a screen with a cursor. One declaration uses one `content` and one session:

```kotlin
import ru.hollowhorizon.hollowengine.common.ui.net.UiSurfaceKind

val Choosing = dataKey<Boolean>("choosing") { false }

surface("project:dialogue") {
    anchor = "hotbar"
    mode { state ->
        if (state[Choosing]) UiSurfaceKind.SCREEN else UiSurfaceKind.OVERLAY
    }
    content {
        Text(if (data[Choosing]) "Choose an answer" else "The story continues")
    }
}
```

Open it on the server with `player.openSurface("project:dialogue")`; `session.put(Choosing, true)` changes the mode without opening another session or losing its data. For UI on a model, use [panel](/docs/hollowengine/scripting/ui/world-panels) instead.

For screens, `guiScale = UiGuiScale.Inherit` follows game settings by default; `guiScale(3)` chooses a fixed scale and `guiScale(0)` selects automatic scaling. On screens, overlays and adaptive surfaces, `exitDuration` keeps the UI mounted for a closing animation, in milliseconds. Closing sets the HSS `:closing` state, which can select an exit animation.

## Kotlin composition

`content { }` is a composable `UiScope` receiver. It can call composables, read `data`, call `send { }`, and call `close()`. Put shared UI in normal Kotlin functions:

```kotlin
@Composable
fun UiScope.Action(label: String, action: String) {
    Box(modifier = Modifier.padding(6.px).onClick { send { putString("action", action) } }) {
        Text(label)
    }
}
```

XML imports are not supported. Reuse Kotlin functions, files, and imports.
