<center><h1>Стейты и корутины</h1></center>

*Определяем разные состояния и переключаемся между ними.*

![Состояния node-скрипта в IDE](/hollowengine/pictures/ide/node-script.webp)

## Что такое стейт и как его создать?

Для создания стейта необходимо добавить к *suspend* функции аннотацию @State

```kotlin
@State
suspend fun main() {

}
```

В параметрах аннотации `@State` можно также указать её имя. Это не обязательно и если его не указывать, будет использоваться имя функции.
Но если вы вдруг решите переименовать функцию, то чтобы не повредить уже существующие сохранения можно указать стабильное название внутри `@State`.

Суть в том, что внутри таких функций можно использовать различные таймеры и ожидания.
Например, можно написать диалог с ожиданиями:
```kotlin
@State
suspend fun main() {
    println("Приветствую, путник")
    wait(2.sec)
    println("Как у тебя дела?")
    wait(2.sec)
    println("Можешь помочь мне с одной просьбой?")
}
```

Тоже самое можно сделать и через `onUpdate`, но выглядит оно куда более громоздко:
```kotlin
var ticker = 0
var фраза = 0

onUpdate {
    // Если диалог закончен, то счётчик больше не обновляется
    if (фраза > 2) return@onUpdate

    // Если количество тиков больше 40 (эквивалентно 2 секундам)
    if (ticker > 40) {
        ticker = 0 // обнуляем счётчик, чтобы следующая фраза была через 2 секунды
        when (фраза) { // пишем текущую фразу
            0 -> println("Приветствую, путник")
            1 -> println("Как у тебя дела?")
            2 -> println("Можешь помочь мне с одной просьбой?")
        }
        фраза++ // Переключаем следующую фразу
    }
    ticker++ // Обновляем счётчик каждую секунду
}
```

То есть через корутины получается куда проще и компактнее.
<br/>
Остаётся лишь вопрос с тем, как сохранять состояние стейта, если он не завершился до выхода игрока, чтобы не пришлось заново читать диалог на 40 минут. Об этом и пойдёт речь далее.

## Сохраняем данные стейта

В текущей архитектуре движок не сохраняет состояние скрипта автоматически. Вместо этого он сохраняет:

- имя текущего стейта;
- `stateTag` текущего стейта;
- дочерние стейты, запущенные через `async`;
- отдельные данные скрипта из `onSave` / `onLoad`.

Это значит, что после перезагрузки мира последний работающий стейт запускается заново с тем же `stateTag`, а не продолжается буквально с той же строки байткода. Поэтому все важные шаги, которые нельзя повторять, нужно помечать через `stateTag`, `runOnce` или `remember`.

### `stateTag()`

`stateTag()` - это функция возвращающая `CompoundTag`, контейнер с данными, привязанный к текущему стейту. Он сохраняется вместе со скриптом и восстанавливается при следующей загрузке мира.

Простейший пример:

```kotlin
@State
suspend fun main() {
    val tag = stateTag()
    if (!tag.getBoolean("greeting_shown")) {
        println("Приветствую, путник")
        tag.putBoolean("greeting_shown", true)
    }

    wait(2.sec)

    if (!tag.getBoolean("question_shown")) {
        println("Можешь помочь мне с одной просьбой?")
        tag.putBoolean("question_shown", true)
    }
}
```

Если сервер сохранится и выключится между двумя фразами, при следующем запуске стейт `main` начнётся заново, но первая фраза уже не повторится, потому что флаг `greeting_shown` лежит в `stateTag`.

Обычно в `stateTag()` стоит хранить только компактные и стабильные данные:

- флаги уже выполненных действий;
- номера шагов;
- UUID сущностей или игроков;
- выбранные варианты диалога (если они не будут использоваться в других стейтах);
- простые значения, которые можно записать в NBT.

Не стоит хранить в локальных переменных `Entity`, `Player` и другие живые объекты, если после `wait`, `delay`, `await` или перезагрузки мира они всё ещё должны быть валидными. Для сущностей и игроков лучше хранить UUID или использовать `Ref`, о котором ниже.

### Чем `stateTag()` отличается от `onSave()` / `onLoad()`?

У `*.node.kts` скрипта есть два уровня сохранения.

Первый уровень - пользовательские данные ноды, сохраняемые через обработчики `onSave` / `onLoad` из [Введения в Node-скрипты](/docs/hollowengine/scripting/node):

```kotlin
onSave { context ->
    context.tag.putInt("reputation", reputation)
}

onLoad { context ->
    reputation = context.tag.getInt("reputation")
}
```

Эти данные сохраняются отдельно от стейтов. Их удобно использовать для глобального состояния ноды: репутации, прогресса квеста, пользовательских настроек, кэшей и прочих данных, которые не принадлежат конкретному стейту.

Второй уровень - данные активных стейтов. Они хранятся в `stateTag()` и нужны именно для восстановления сценария: какой шаг уже был выполнен, какой NPC был создан, какую ветку диалога выбрал игрок.

Упрощённо это можно представить так:

```text
node.nbt
├─ extras  -> данные из onSave / onLoad
└─ states  -> активный StateContext
   ├─ next_state
   ├─ self     -> stateTag
   └─ children -> дочерние async-стейты
```

Поэтому правило простое:

- **данные ноды** сохраняем через `onSave` / `onLoad`;
- **данные выполнения конкретного стейта** сохраняем через `stateTag`, `runOnce`, `remember` и `forget`.

## Переключаемся между несколькими стейтами

Стейты можно разбивать на небольшие функции и переключаться между ними.

```kotlin
@State
suspend fun main() {
    println("Нужно поговорить с кузнецом")
    wait(1.sec)

    blacksmithDialog()
}

@State(name = "blacksmith")
suspend fun blacksmithDialog() {
    println("Кузнец: Мне нужна руда из старой шахты")
    wait(2.sec)

    mineQuest()
}

@State(name = "mine_quest")
suspend fun mineQuest() {
    println("Задание обновлено: найти старую шахту")
}
```

Важно: вызов одного `@State suspend` из другого `@State suspend` - это **не обычный вложенный вызов функции**.
Компиляторный плагин HollowEngine на этапе IR заменяет такой вызов на переход к другому стейту.
**То есть после завершения `@State`-функции возврата в прошлую функцию не будет.**

Такой подход делает переходы явными для runtime: движок меняет `nextState`, завершает текущий стейт, а затем запускает следующий.

## Вспомогательные функции

### `runOnce`

`runOnce` нужен для действий, которые нельзя повторять после рестарта стейта.

```kotlin
@State
suspend fun main() {
    runOnce("give_map") {
        println("Игрок получил карту")
        // player.update { inventory.add(ItemStack(...)) }
    }

    wait(10.sec)
    println("Этот текст может выполниться после восстановления")
}
```

Под капотом это тот же принцип, что и ручной флаг в `stateTag()`: если ключ уже отмечен как выполненный, блок больше не запускается.

Используй `runOnce` для необратимых действий:

- выдать предмет;
- заспавнить NPC;
- изменить блоки в мире;
- отправить одноразовое сообщение;
- начислить награду;
- воспроизвести длинный диалог.

### `remember`

`remember` удобно использовать, когда нужно один раз вычислить значение и затем переиспользовать его при повторном запуске стейта.

Например, если стейт создаёт NPC, не стоит создавать его заново после каждой загрузки мира. Лучше запомнить UUID и потом работать через `entityRef`:

```kotlin
@State
suspend fun main() {
    val traderId = remember("trader_uuid") {
        spawnTrader().uuid
    }

    val trader = entityRef<LivingEntity>(traderId)

    trader.update {
        customName = "Таинственный торговец".literal
    }
}
```

### `forget`

`forget` удаляет сохранённое значение, если сценарий нужно пройти заново.

```kotlin
@State
suspend fun resetQuest() {
    forget("trader_uuid")
    forget("give_map")

    main() // Учтите, тут имеется ввиду обычная suspend функция, а не State, при переходе в другой State, у него другой stateTag()
}
```

Это полезно для повторяемых сцен, тестирования, отката ветки диалога или перезапуска квеста.

## Ожидание, переживающее перезапуск

Обычный `wait(ticks)` (см. [Служебные методы](/docs/hollowengine/scripting/npc/methods)) - это просто таймер: если стейт перезапустится, пока он ещё отсчитывает время, то по правилам в начале этой страницы стейт начнётся заново с первой строки, и отсчёт начнётся с нуля. Для короткой паузы внутри диалога это нормально, но не подходит для чего-то вроде "подожди 5 минут" или "раз в день", что должно продолжать отсчёт даже после перезапуска сервера.

Для этого ожиданию можно установить стабильное имя `name`, точно так же, как `runOnce` и `remember` используют своё:

```kotlin
@State
suspend fun main() {
    wait(20 * 60 * 5, "patrol_pause") // 5 минут, считается только пока сервер работает
}
```

Есть ещё два варианта для реального времени, включая время, пока сервер был полностью выключен:

```kotlin
@State
suspend fun main() {
    npc.say("Возвращайся завтра за наградой!")
    wait(1.days, "daily_reward_cooldown") // считает реальное время, даже пока сервер выключен
    npc.say("Твоя награда готова!")
}
```

```kotlin
@State
suspend fun main() {
    wait(Instant.parse("2026-12-25T00:00:00Z"), "christmas_event") // ждёт до конкретной даты
    npc.say("С праздником!")
}
```

| Функция | Считает | Продолжает считать, пока сервер выключен? |
|---------|---------|---------------------------------------------|
| `wait(ticks)` | игровые тики | Нет, отсчёт начинается заново, если стейт перезапустился. |
| `wait(ticks, name)` | игровые тики | Нет, но продолжает отсчёт, с последнего тика до остановки. |
| `wait(duration, name)` | реальное время | Да. |
| `wait(instant, name)` | реальное время, до конкретной даты | Да. |

Как и `runOnce` и `remember`, дедлайн хранится в `stateTag()`, поэтому работает по тем же правилам сохранения/восстановления и именования. Используйте разные `name` для каждого постоянного ожидания в скрипте, чтобы они не перезаписывали друг друга.

## Запуск

Запуск также реализуется командой, разница лишь в том, что нужно явно указать имя стейта / функции:
```mcfunction
/hollowengine scripting run scripts/your_script.node.kts startQuest
```
И чтобы остановить соответственно:
```mcfunction
/hollowengine scripting stop scripts/your_script.node.kts
```

## Сюжетная часть

Во время сценариев часто хочется сохранить NPC или игрока в переменную и продолжить работать с ним после `wait`:

```kotlin
@State
suspend fun main() {
    val npc = spawnTrader()
    wait(60.sec)
    npc.remove(RemovalReason.DISCARDED)
}
```

Такой код выглядит удобно, но у него есть проблема: за время ожидания сущность может выгрузиться, умереть, сменить уровень или стать невалидной. Поэтому для долгих сценариев лучше хранить не сам объект, а ссылку `Ref<T>`.

`Ref<T>` умеет:

- проверить, жива ли ссылка через `isLinkAlive`;
- дождаться объекта через `resolve()`;
- безопасно прочитать данные через `read { ... }`;
- безопасно изменить объект через `update { ... }`.

Пример с NPC:

```kotlin
@State
suspend fun main() {
    val npcId = remember("trader_uuid") {
        npc(pos(x, y, z), name="Торгаш").uuid
    }

    val trader = entityRef<LivingEntity>(npcId)

    wait(60.sec)

    // Если нпс успел выгрузиться из чанка, скрипт будет ждать, пока чанки прогрузятся
    trader.update {
        remove(Entity.RemovalReason.DISCARDED)
    }
}
```

Пример с игроком:

```kotlin
@State
suspend fun main() {
    val player = playerRef("Steve") // Можно получить ссылку по нику или uuid: `playerRef(uuid("12346-..."))`

    player.update {
        send("Ты готов?")
    }
}
```

Если нужно одновременно получить несколько ссылок и убедиться, что они всё ещё актуальны, можно использовать `borrow`:

```kotlin
@State
suspend fun attackTarget() {
    val attacker = entityRef<LivingEntity>(stateTag.getUUID("attacker"))
    val target = entityRef<LivingEntity>(stateTag.getUUID("target"))

    borrow(attacker, target) { me, them ->
        me.doHurtTarget(them)
    }
}
```

`borrow` нужен для ситуаций, когда между получением первой и второй сущности одна из них могла успеть выгрузиться. Он повторяет получение до тех пор, пока все ссылки не будут живыми одновременно.

Главное правило для сюжетных сценариев:

```text
короткое действие прямо сейчас или рядом с игроком -> можно работать с Entity / Player
долгий сценарий с wait/await/requestItems -> лучше хранить UUID и использовать Ref<T>
```

Так стейты остаются устойчивыми к выгрузке чанков, выходу игрока и сохранению мира.
